Quick start and sign-in

  1. Open the app and use Email + Password for normal access.
  2. Use Magic Link or Account Recovery only when normal sign-in is unavailable.
  3. After sign-in, the application loads only the active module your profile may use; other permitted modules load when you navigate to them.
  4. Use the top Help link at any time to return here.

Account recovery

Use your employee number plus the requested secondary check. Never send a password, recovery token, payment-card number, or secret API key in a support message.

Profile, Crew and reference data

My Profile renders the signed-in profile record first so the screen stays useful while its live refresh is running. Profile and time-clock reads are requested only while the Profile route is open. Crew data loads only when the Crew route is open and your role has Crew access; opening Profile does not preload the Crew directory.

Shared site, employee, supervisor, admin, position and trade reference data is reused for a short freshness window instead of being fetched repeatedly on every protected-screen event. Concurrent identical refreshes share one request, changing identity or signing out invalidates the cached reference set, and a successful profile save invalidates it so later selectors can refresh. A reference-data refresh failure must not blank an already usable screen; reload the relevant screen if you need a fresh list immediately.

Mobile phone workflow

  • The Today screen starts with What needs attention now. Offline work, sync conflicts, saved drafts, and queued work take priority before ordinary shortcuts.
  • Today groups shortcuts into Now / work, Safety & field, and Supervision & admin so the next action is easier to find without loading another module.

Live update records field progress with explicit staff/customer visibility. Execution proof captures arrival/completion evidence and internal labour, material and equipment context for authorized supervisor review. Customer service update emails

Customer notification delivery is consent-first. Email service-update notifications require an explicit opt-in in the secure customer portal; if the customer has not opted in, no delivery should be attempted. Emails may point back to the secure portal for customer-safe details but must not contain staff-only notes, private images, access information, internal costing or margin context.

Operations may review bounded delivery states such as pending consent, delivered and manual review. Uncertain transport must remain in manual review rather than being assumed delivered or retried automatically. Retry is an explicit staff action after review, and the delivery queue must not expose customer email addresses or portal tokens merely to inspect delivery status.

Finance

Finance access is permission-controlled. Start from Finance Overview, then open only the workspace you need: Review Queue, Posting Controls, Reconciliation, Close & Tax, or Account Mapping. The completed-job review authority and posting control-plane authority are deliberately deferred until their matching workspace is selected, so opening Finance does not automatically run every deep Finance read.

Posting execution and payment-provider mutation remain fail-closed unless an authorized release explicitly enables them. Choosing a workspace changes presentation and read timing only; it does not grant authority or enable posting.

Bank Import Workbench v2

Bank CSV review is a staged Finance workflow. Choose the source file, map Date, Description and either Amount or Debit/Credit, then save the bank/account column mapping on the current device when the format is reusable. The browser records a SHA-256 source fingerprint and file size with the preview so later import history can identify the reviewed source without exposing the file itself.

I.T. Release & Deployment Cockpit

The Release & Deployment Cockpit is a read-only orientation layer inside I.T. Readiness. It presents one ordered path through Source / CI → Database → Repository → Acceptance → manual Production promotion, then identifies the next safe release action from the same bounded runtime payload already loaded by I.T. Readiness. It does not add another release query and it intentionally has no deploy or promote button.

Application performance budget: the canonical source/browser workflow enforces a maximum Core shell of 30 cached assets / 21 JavaScript assets; permission-driven module caps of Safety ≤ 10 scripts, Finance ≤ 3, Jobs ≤ 4, and Admin ≤ 8; and at most 10 bounded source reads for the interactive I.T. runtime. Today remains local-state driven, its background refresh stays at 30 seconds or slower, Finance review/posting reads remain workspace-selected, and deep account mapping remains explicitly on demand. Increasing a budget requires a deliberate source change and regression review rather than silently restoring eager loading.

Admin status chips and Needs Attention are orientation aids. READY means currently loaded bounded evidence is healthy; ACTION means operator review is required; BLOCKED means a current runtime/authority failure is visible; OPEN TO LOAD means the deeper evidence has not yet been requested. None of these statuses auto-close work, change permissions, enable Finance/provider mutation, mutate Auth, sign off staging, or promote Production.

Use Current Admin To-Do for unresolved work. The Production readiness panel is derived from current schema, exact-source release authority, repository enforcement, scorecard classification, current Admin To-Do, public search/Help authority, and Finance/provider safety. Historical prerelease and foundation checklist rows are retained only as audit history and must not be treated as current work.

External Auth/GitHub controls remain evidence-driven, content/provider work remains pending until its required approval or test evidence exists, and accounting work remains blocked while Finance posting execution and provider mutation are OFF.

Auth security evidence

Leaked-password protection and MFA options are external Supabase Auth settings. A control may be treated as secure only when recent authoritative evidence comes from the Supabase Dashboard or Supabase Management API, includes a durable source reference, and reports the secure state for that specific control. Manual notes, screenshots or other supporting context may be retained, but manual_external evidence is non-authoritative and cannot produce a verified-secure result. Supabase advisor rows, historical warnings, database catalogs, or the absence of an advisor warning are also not proof of the current setting. Evidence older than the freshness window must be re-verified, and the Current Admin To-Do remains open until valid control-plane evidence exists.

Auth evidence intake: the lower-level engineering intake remains npm run auth:evidence:intake -- <input.json>. It accepts only Dashboard/Management API provenance for the exact registered project, requires a current timestamp and durable reference, derives the control-specific verification status, rejects supplied authority/status/expiry overrides and credential-bearing fields, and writes only a digest of the raw capture into the candidate. Passing intake validates structure and freshness only; source authenticity is still external and the tool does not authorize a database write.

Preferred GitHub Auth evidence workflow: manually run YWI Auth security evidence capture from main and wait for it to succeed. Retain the exact GitHub run ID and attempt. Then manually run YWI Auth evidence authorized recording from main, supplying that exact capture_run_id and capture_run_attempt. Select exactly one control, leaked_password_protection or mfa_options, and set I_CONFIRM_AUTH_EVIDENCE_RECORD plus I_CONFIRM_OFFICIAL_SUPABASE_SOURCE only after confirming the capture is genuine current official Supabase Management API evidence. The workflow is intentionally one control per dispatch; run it separately for the second control when required. It downloads only the exact encrypted capture package, decrypts and re-binds it on the ephemeral runner, invokes the existing service-private recorder, and destroys the plaintext workspace. It records evidence only and does not change Auth settings. After each recording, refresh I.T. Readiness → Access & Security and confirm the current evidence state rather than marking the follow-up complete by hand.

Lower-level authorized Auth evidence recording: controlled engineering use may still run npm run auth:evidence:record -- <candidate.json> with the exact Production Supabase URL/project, a service-role credential, YWI_AUTH_EVIDENCE_RECORD_CONFIRM=I_CONFIRM_AUTH_EVIDENCE_RECORD, and YWI_AUTH_EVIDENCE_SOURCE_AUTHENTICITY_CONFIRM=I_CONFIRM_OFFICIAL_SUPABASE_SOURCE. The database RPC independently re-validates the project, official source, freshness, durable reference, capture digest and control-specific state, derives status/expiry, records idempotently, and immediately re-reads current Auth evidence. A mismatch stays locked.

Repository enforcement preflight

GitHub branch enforcement is external evidence, not something a green source workflow may infer. On an exact push to main, the release workflow reads GitHub's current branches/main state, requires protected=true, and requires the GitHub-reported branch SHA to exactly match the workflow release SHA. A pull-request pass, a stale branch lookup, or a different SHA cannot authorize release-green repository enforcement. This preflight does not enable branch protection or change GitHub rulesets; the repository follow-up remains open until GitHub itself reports enforcement.

Exact-main release-source evidence

After the complete source/browser job succeeds on an actual main push, a dependent job re-reads GitHub's current branches/main state and re-runs the exact-main protection gate. It then writes release-source-evidence.json and uploads a run-scoped ywi-main-release-source-<run-id>-<attempt> GitHub Actions artifact containing the exact SHA, run identity, workflow name, repository schema version, source-check result, and observed protected state.

The artifact is a release-source candidate, not deployment proof. It intentionally keeps branch_policy_verified=false and the database-record candidate workflow_status=unknown; the workflow cannot prove its own final conclusion while it is still running.

After the exact workflow run has completed, collect that completed run response plus a fresh current branches/main response and run npm run release:evidence:verify against the candidate. The verifier requires exact repository, workflow name/path, push event, main branch, run ID/attempt, source SHA, current source schema, completed/success state, current main SHA and protected=true. Only then may it write release-source-evidence-verified.json with workflow_status=passed. A failed or in-progress run, moved main branch, schema/run mismatch, wrong repository/workflow, or unprotected main stays locked and removes stale verified output.

Even verified evidence keeps branch_policy_verified=false until detailed GitHub ruleset/protection-policy evidence exists. Verification does not write Supabase release evidence, mutate Production, enable Finance/provider mutation, deploy or promote Production, or close a release/business rail.

Authorized release evidence recording: record only a final verified payload with npm run release:evidence:record -- <verified.json>. The command performs a fresh GitHub run and current-main lookup immediately before recording, requires the exact Production Supabase URL/project, service-role credentials, YWI_RELEASE_EVIDENCE_RECORD_CONFIRM=I_CONFIRM_RELEASE_EVIDENCE_RECORD, a recent final verification, and exact Production/source schema parity. A moved SHA, crossed attempt, failed run, unprotected main, stale verification, or schema mismatch stays locked.

The database derives workflow_status=passed; callers do not supply status or detailed branch-policy truth. The record stores run attempt, canonical workflow path and a SHA-256 verified-payload digest, then immediately re-reads current release authority. Direct release-evidence table writes and the legacy permissive recorder remain disabled. Recording source evidence still does not deploy or promote Production.

Staging mutation guard

Staging acceptance evidence writes are never allowed merely because the I.T. panel is visible. Production may read status/catalog information, but Pass/Fail evidence, Finalize, and Signoff remain locked unless the endpoint proves a dedicated non-production staging runtime.

Before human staging evidence is enabled, the staging function must have YWI_RUNTIME_ENVIRONMENT=staging, YWI_STAGING_PROJECT_REF matching the exact current staging project, and YWI_STAGING_ACCEPTANCE_MUTATION_ENABLED=true. The registered Production project is always denied. The I.T. panel shows whether the environment guard is ENABLED or LOCKED; do not bypass a locked state.

GitHub staging runner preflight: before the manual staging workflow starts, npm run staging:preflight derives the project ref from the HTTPS SUPABASE_URL hostname and requires it to exactly match YWI_STAGING_PROJECT_REF. A staging ref that is merely different from Production is not enough. Both the permanently known Production ref and any configured Production ref remain denied, even if one setting is crossed or overridden. The preflight may show project refs and whether credentials are present, but it must never print service-role keys, public keys, JWTs, or other secret values.

Exact current-schema parity is a second independent lock. The I.T. staging panel reads v_schema_drift_status and shows the expected repository schema and latest applied staging schema. Human staging mutation remains unavailable unless drift is current and those two schema versions match exactly. A staging database that is behind or ahead of source remains locked. The historical Schema 187 scenario catalog remains the catalog authority; it is not the current execution schema label.

Environment + schema are both required. Passing one guard never bypasses the other. Staging evidence and human signoff do not automatically close a scorecard rail; they remain evidence for a later deliberate release decision.

If no dedicated non-production project or branch exists, do not run or claim live staging evidence; Production is never a substitute.

Offline and sync

  • An offline banner means live reads, uploads, sign-in, and server writes may be unavailable.
  • Field sync health separates queued forms, saved drafts, queued actions, and conflicts instead of treating “online” as “fully synchronized.”
  • Keep local drafts and queued work until the server confirms the write.
  • Do not repeatedly submit the same action if the app reports an in-progress or conflict state.
  • After connectivity returns, review the sync state and confirm the resulting server status before removing local evidence.

Troubleshooting

  • Screen missing: confirm you are signed in and that your profile has access to that module.
  • Page keeps loading: reload once, then check the offline banner and I.T. Readiness if you have Admin access.
  • Finance feels too long: return to Finance Overview and open only Review Queue, Posting Controls, Reconciliation, Close & Tax, or Account Mapping as needed. Review/posting server reads are intentionally deferred until their workspace is selected.
  • I.T. Readiness feels too long: use the five domain cards and expand only the relevant domain; blocked domains open automatically.
  • Release cockpit says manual: that is intentional. Use its next-safe-action cue to resolve source, schema, repository, To-Do, or acceptance blockers, then use the established deliberate release process; the cockpit itself cannot deploy or promote.
  • Performance budget gate fails: identify which shell/module/read budget increased. Reduce eager loading or deliberately review and update the budget contract with matching source/browser evidence; do not simply remove the gate.
  • Admin feels too long: return to Admin Home and open only the card you need; use Admin search for a specific panel and expand a collapsed panel only when required.
  • Stale interface: close old tabs and reload so the current service worker and assets take control.
  • Write rejected: read the returned reason; do not bypass role, approval, environment, schema, or release gates.
  • Sync conflict: review the local queued action and current server record before retrying. Do not assume the newer timestamp is automatically the correct version.
  • Next action seems unsafe: use the safety note in I.T. Readiness and re-check the required environment/schema/external/provider/accounting guard before acting.
  • Auth security follow-up: use the two-step GitHub Actions sequence above: successful read-only capture first, then authorized recording for one selected control with the exact capture run ID/attempt and both explicit confirmations. Refresh I.T. Readiness after recording; never infer completion from the workflow result alone.
  • Repository enforcement locked: verify GitHub reports the current exact main SHA as protected; a green PR/source run is not sufficient evidence.
  • Release-source candidate: never change its unknown workflow status by hand. Wait for the exact run to complete, then use fresh run/main evidence with npm run release:evidence:verify; only release-source-evidence-verified.json may contain workflow_status=passed.
  • Release-source recording locked: rerun final verification if needed, then use release:evidence:record with I_CONFIRM_RELEASE_EVIDENCE_RECORD. The recorder must see the same successful run/attempt, the same protected current main SHA, exact Production schema parity, and a fresh verification before it will write or re-read evidence.
  • Staging control locked: confirm the staging preflight reports an exact URL/project-ref match on a non-Production target, the environment guard is enabled, and Runtime schema authority reports CURRENT with matching expected/live schema versions. Production must remain locked.
  • Public page missing: it may not be approved/published yet; use the public contact form instead.

Build 329 — Incident & Near-Miss Investigation

Build 330 — Training & Certification Matrix

Build 332 — Daily Equipment Inspection & Lockout

Build 332 adds machine/category-specific pre-use and post-use inspection checklists while keeping equipment_items as the asset authority and equipment_service_tasks as the repair/service authority. Checklist areas cover guards and safety systems, fluids/leaks, blades or cutting components, tires/wheels, fuel/battery, accessories, damage and defects.

A safety-critical failure is fail-closed: the inspection record is saved, the equipment is locked out, defect evidence is written to the existing asset, and a high-priority inspection service task is created. A non-critical failed item is kept as needs-review evidence rather than silently clearing the asset.

Supervisor review is a separate explicit action. For a safety-critical failure, approval alone does not return the equipment to service. The linked repair/service task must first be resolved or cancelled with appropriate evidence, after which an authorized operator must explicitly verify return to service.

Safety boundary: a passed checklist, supervisor approval or verified return to service is operational evidence, not a legal-compliance certificate. Operators must still follow manufacturer instructions, training/authorization requirements and applicable workplace-safety law.

Build 333 — Fleet, Trailer & Vehicle Operations

Build 333 treats trucks, trailers and fleet vehicles as existing equipment_items, then adds fleet-specific identity and operating evidence for plate/VIN or unit reference, registration and insurance expiry, annual vehicle inspection due dates, tire condition, hitch/tow capacity, trailer connector and fuel type.

Towing assignments are compatibility-gated. Boundary: Build 333 records operational fleet evidence; it does not certify legal roadworthiness, insurance validity or driver qualification. Preventive-maintenance scheduling is handled separately by Build 334 so fleet readiness and maintenance scheduling remain distinct operational authorities.

Build 334 — Preventive Maintenance Engine

Build 334 reuses equipment_items, equipment_service_history and equipment_service_tasks as the existing asset, service-history and repair/work authorities. Preventive plans can be based on calendar days, operating hours, kilometres or an annual seasonal milestone.

Plan types cover oil, filters, blades, sharpening, belts, lubrication, tires, batteries, winterization, storage, preseason setup, repairs, inspections and general service. Each plan records its next date or meter threshold, warning lead, provider/cost estimate and instructions. The workbench distinguishes scheduled, due-soon, due and overdue work.

Due work can create one linked preventive-maintenance service task. Completion records the actual service in the existing service history, closes the linked task when appropriate, captures cost/provider/meter evidence, and advances the next date, meter or seasonal milestone.

Safety boundary: preventive-maintenance completion does not automatically clear a safety lockout, defect, failed inspection or return-to-service block. Those remain separate explicit safety controls.
