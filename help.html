Quick start and sign-in

  1. Open the app and use Email + Password for normal access.
  2. Use Magic Link or Account Recovery only when normal sign-in is unavailable.
  3. After sign-in, the application loads only the modules your profile may use.
  4. Use the top Help link at any time to return here.

Account recovery

Use your employee number plus the requested secondary check. Never send a password, recovery token, payment-card number, or secret API key in a support message.

Mobile phone workflow

  • Use the bottom module shortcuts for Safety, Finance, Jobs, and Admin.
  • The Today screen is the fastest starting point for field work.
  • Forms are phone-first and may keep a local draft when connectivity is interrupted.
  • If a sync conflict appears, review the local and server versions before replacing either copy.
  • QR/barcode scanning includes a manual fallback when camera scanning is unavailable.

Safety / OHSA

Use Safety / OHSA for toolbox talks, PPE checks, first-aid checks, incidents and near misses, site inspections, drills, logbook work, and historical safety reporting. Follow the form prompts and attach only appropriate evidence.

Jobs

Use Jobs for current work, crew/job context, equipment, service execution proof, and supervisor workflows available to your role.

Finance

Finance access is permission-controlled. Review accounting, reconciliation, close, mapping, and posting-readiness information only within the authority granted to your profile. Posting execution and payment-provider mutation remain fail-closed unless an authorized release explicitly enables them.

Human accounting decisions

Account mapping approvals remain an accountant/bookkeeper decision. Suggestions and compatibility indicators do not auto-approve a mapping.

Admin and I.T. Readiness

Admin contains profile/module management, operations controls, security/readiness evidence, staging acceptance, release authority, and I.T. Readiness. I.T. Readiness is part of Admin; it is not a separate top-level module.

Use Current Admin To-Do for unresolved work. The Production readiness panel is derived from current schema, exact-source release authority, repository enforcement, scorecard classification, current Admin To-Do, public search/Help authority, and Finance/provider safety. Historical prerelease and foundation checklist rows are retained only as audit history and must not be treated as current work.

Next safe action

The next safe action authority ranks the current unresolved queue without taking action for you. A staging item marked as a ready candidate still requires the dedicated non-production staging environment guard to be verified immediately before any mutation. External Auth/GitHub controls remain evidence-driven, content/provider work remains pending until its required approval or test evidence exists, and accounting work remains blocked while Finance posting execution and provider mutation are OFF.

The priority view never auto-closes a business rail, changes an Auth setting, publishes public content, enables Finance/provider mutation, or promotes Production.

Auth security evidence

Leaked-password protection and MFA options are external Supabase Auth settings. Keep each Current Admin To-Do item open until recent authoritative external evidence verifies the actual setting. Supabase advisor rows, historical warnings, or the absence of an advisor warning are not authoritative external evidence and must not be used to infer that either setting is secure. Evidence older than the current freshness window must be re-verified before it can support readiness.

Staging mutation guard

Staging acceptance evidence writes are never allowed merely because the I.T. panel is visible. Production may read status/catalog information, but Pass/Fail evidence, Finalize, and Signoff remain locked unless the endpoint proves a dedicated non-production staging runtime.

Before human staging evidence is enabled, the staging function must have YWI_RUNTIME_ENVIRONMENT=staging, YWI_STAGING_PROJECT_REF matching the exact current staging project, and YWI_STAGING_ACCEPTANCE_MUTATION_ENABLED=true. The registered Production project is always denied. The I.T. panel shows whether the environment guard is ENABLED or LOCKED; do not bypass a locked state.

Exact schema is a second independent lock. The I.T. staging panel reads v_schema_drift_status and shows the expected repository schema and latest applied staging schema. Human staging mutation remains unavailable unless drift is current and those two schema versions match exactly. The historical Schema 187 scenario catalog remains valid history; it is not the current execution schema label.

Staging evidence and human signoff do not automatically close a scorecard rail. They remain evidence for a later deliberate release decision.

Customer portal and public pages

Customer quote links are token-protected. Only customer-safe information should appear there. Staff notes, internal costing, access details, and private review media must stay internal.

Public service pages are published only from approved content. They use exactly one page-level H1, canonical URLs, crawlable HTML, and canonical-only sitemap entries. Sitemap freshness (lastmod) must reflect a meaningful content change rather than simply the deployment date.

Search/index boundary

yardweasels.ca is the canonical public authority for this operations application and its approved service routes. The established ywiinc.com business website is a separate public presence and is not used as a cross-domain canonical unless a deliberate future page-mapping decision proves the equivalent page exists there. Preview or other noncanonical hosts must remain noindex; their rendered pages still point canonically to yardweasels.ca. If an approved route and supplied canonical disagree, the page fails closed to noindex until the conflict is corrected.

Search discovery and structured data

Public structured data must mirror the visible page and current authority, including webpage, service, and breadcrumb semantics. Phone and desktop webpage acceptance verifies the same H1, canonical, indexing, structured data, and responsive-layout rules. External search-engine submission, including IndexNow or Search Console actions, is not automatic; it requires an explicit configured action and must never publish an unapproved route.

Offline and sync

  • An offline banner means live reads, uploads, sign-in, and server writes may be unavailable.
  • Keep local drafts until the server confirms the write.
  • Do not repeatedly submit the same action if the app reports an in-progress or conflict state.
  • After connectivity returns, reload or retry from the relevant screen and confirm the resulting status.

Troubleshooting

  • Screen missing: confirm you are signed in and that your profile has access to that module.
  • Page keeps loading: reload once, then check the offline banner and I.T. Readiness if you have Admin access.
  • Stale interface: close old tabs and reload so the current service worker and assets take control.
  • Write rejected: read the returned reason; do not bypass role, approval, environment, schema, or release gates.
  • Next action seems unsafe: use the safety note in I.T. Readiness and re-check the required environment/external/provider/accounting guard before acting.
  • Auth security follow-up: use current Supabase Auth control-plane evidence; do not close leaked-password or MFA work from advisor silence.
  • Staging control locked: confirm you are using the dedicated staging project, the environment guard is enabled, and Runtime schema authority reports CURRENT with matching expected/live schema versions. Production must remain locked.
  • Public page missing: it may not be approved/published yet; use the public contact form instead.
Release safety: Production promotion remains deliberate. Finance execution, provider mutation, Auth setting mutation, staging acceptance mutation, human acceptance, content publication, external search submission, and external-provider acceptance must never be inferred from a green source test alone.
